# Controlled recovery in Agent Services

The owner-authorized four historical originals now have a small panel in the existing authenticated `/services` workspace. The customer sees only the three originals bound to its authenticated wallet; the original administrator sees only its one original. No console helper, session transfer or administrator impersonation is needed.

The panel reuses `POST /api/service-payments/:id/recover-expired` with the unchanged strict confirmation body. Each record displays its actual recorded payer, original ID/digest and 0.001 SUI reservation. One checkbox and one button confirm only the next original. The existing procedure still performs fresh Mainnet, protocol, expiry, digest, independent provider coverage, closed-boundary, settlement, ownership and complete-liability checks; its release and audit transaction is unchanged.

`GET /api/service-payments/recovery` is an authenticated, private/no-store, database-enforced read-only snapshot. It returns only the caller's exact approved originals, the actual recovery-enabled boolean, minimal successful-audit identifiers and aggregate wallet/sponsor liabilities. It validates original transaction bindings, checks exactly one matching successful audit and its retained independent evidence, and verifies the entire current liability calculation. Other workspaces' records, transaction bytes, session identifiers, raw audit/provider messages and credentials are not returned. The all-originals-closed indicator is read-only operator context; it grants no access to another workspace and does not gate independent customer checkout. The customer gate uses its own verified originals and liabilities plus the global recovery-window flag. An administrator reservation is excluded from the public sponsor ledger and cannot consume this customer’s allowance.

After every POST, the panel makes this independent persisted-state read before unlocking the next checkbox. HTTP success alone is insufficient. No next POST, quote, preparation, wallet prompt or signing operation happens automatically. A pending-attempt marker is saved before the request. A failed/uncertain response remains stopped across reloads and cannot resume through refresh until the recovery window is closed and the persisted result is coherent. Refresh never repeats a POST. A server-held review or accounting/audit discrepancy blocks the sequence.

The actual runtime flag is visible in the panel and through the same authenticated read-only endpoint. The owner restores only `SERVICE_EXPIRED_RECOVERY_ENABLED=false` for Production and redeploys. The disabled runtime value and live release are then verified read-only. After all originals in the authenticated customer workspace are verified and the window is disabled, the customer panel offers the existing `PG-TEST-1103-01` Harborline checkout. Later normal purchases remain fully counted without invalidating the historical recovery audits.

No financial authorization model, signing implementation, expiration rule, provider evidence requirement, spending cap, invoice, receipt, memory, video or branding change is included. There is no migration, SQL mutation path, force-release switch or cross-workspace recovery endpoint. The normal Harborline quote, terms approval, unsigned preparation and personal Nightly financial signature remain separate actions. The agent must not click **Sign and submit** or trigger the wallet prompt.

Validation uses isolated disposable database tests and explicitly mocked financial browser fixtures. Production execution is claimed only after the real authenticated requests and their persisted audits, exact ledger deltas and protected-record fingerprints have been inspected.
